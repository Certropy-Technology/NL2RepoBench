# `json5` static Node v2 pilot audit

**Status: development-only static candidate; publication blocked.** The narrow
CommonJS root API is feasible for a future JSON-only Node v2 task, but this
record is not a task descriptor, Harbor bundle, publication approval, or test
artifact. It contains no upstream test bytes, hidden/private tests, private
command plan, npm cache or dependency tarball, Dockerfile, verifier, Oracle,
reward, secret, generated package, or shared catalog/index edit.

The proposed score surface is only the root package object's `parse` and
`stringify` functions through a bounded JSON request/response child. The CLI,
`require.extensions` registration hooks, deprecated deep import, browser UMD
build, generated ESM build, callbacks, and JavaScript-only values are out of
scope. A later task must use one reviewed module format rather than implicitly
claiming parity across every entry point in the upstream package.

## Package metadata and CJS/ESM export audit

The locked manifest has no `type` field and no `exports` map. Its relevant
entry metadata is:

```text
main:    lib/index.js
module:  dist/index.mjs
browser: dist/index.js
bin:     lib/cli.js
types:   lib/index.d.ts
files:   lib/, dist/
engines: node >=6
```

`lib/index.js` is CommonJS and assigns an object containing `parse` and
`stringify` to `module.exports`. The exact source tree contains no tracked
`dist/` directory; `.gitignore` excludes it. Therefore the `module` and
`browser` targets are not immutable source files at this revision. An
exact-checkout `npm pack --dry-run --ignore-scripts` listed 16 files and no
`dist` member. The resulting source-only package still has a functional
CommonJS root:

```text
require("json5") keys -> parse, stringify
import("json5") keys  -> default
import("json5").default keys -> parse, stringify
```

Node treats `module` as a bundler convention, not a conditional package
export. Root ESM import therefore resolves the CommonJS `main` and does not
expose top-level named `parse` or `stringify` bindings.

For disposable build evidence, `npm run build` completed under Node `22.23.1`
and generated four ignored files:

```text
dist/index.js       58,620 bytes, UMD
dist/index.min.js   31,631 bytes, minified UMD
dist/index.mjs      46,428 bytes, ESM
dist/index.min.mjs  29,473 bytes, minified ESM
```

All four generated files passed `node --check`. The ESM bundle exports one
default object whose keys are `parse` and `stringify`; it does not provide
named exports. A post-build package had 20 files and loaded through the deep
`json5/dist/index.mjs` path, but those generated bytes are not source-locked
and were discarded.

The initial task should consequently score only the directly source-locked
CommonJS root object. It must exclude `dist`, `browser`, `lib/cli.js`,
`lib/register.js`, `lib/require.js`, and arbitrary deep imports. Requiring both
CJS and ESM output would introduce a separate build/packaging decision and a
second export contract; that is not approved by this static lane.

## JSON parse/stringify subprocess boundary

The two root functions are callable by the repository's fixed Node child
protocol because CommonJS `require("json5")` exposes literal function-valued
`parse` and `stringify` properties. Ordinary probes through that protocol
returned JSON-compatible results for JSON5 input and structured failures for
syntax errors. Candidate code remained in the child process; no trusted
Python process imported it.

A future public contract can use the following JSON-only surface.

### `parse(text)`

- `text` is a bounded string. Although upstream coerces other values with
  `String(text)`, non-string requests should be rejected by the public task
  contract.
- Supported syntax may include JSON plus JSON5 comments, single-quoted
  strings, unquoted identifier keys, trailing commas, hexadecimal numbers,
  explicit plus signs, leading/trailing decimal points, JSON5 whitespace, and
  nested arrays/objects.
- The returned value must remain representable without loss as JSON: `null`,
  booleans, finite numbers, strings, arrays, and string-keyed objects.
- Invalid input raises `SyntaxError`. Upstream attaches `lineNumber` and
  `columnNumber`, while the generic child currently reports only exception
  type and message. The private adapter must either freeze that generic error
  projection or add a separately reviewed JSON projection before assertions
  rely on the numeric fields.

JSON5's `NaN`, positive/negative `Infinity`, and negative-zero distinction are
not transparent through the current response encoder. A direct child probe of
`[NaN,Infinity,-Infinity,-0]` returned `[null,null,null,0]` because the trusted
protocol serializes responses with `JSON.stringify`. These values must be
excluded unless a future task-specific tagged-number protocol is explicitly
reviewed. The optional function-valued `reviver` is also excluded. Unescaped
U+2028/U+2029 values can emit `console.warn`; warning behavior is not part of
the proposed score contract.

### `stringify(value, replacer?, space?)` / `stringify(value, options)`

- `value` is limited to JSON values, so the result is a JSON5 string and the
  request cannot smuggle executable callbacks or custom prototypes.
- A JSON array of string/number property names may be used as `replacer`.
  Function replacers are excluded.
- `space` may be a JSON string, finite number, or `null`, with the documented
  ten-character/ten-space cap.
- The JSON options form may contain only `replacer`, `space`, and `quote`;
  `quote`, when present, should be restricted to a single quote or double
  quote.
- Array order and JavaScript object enumeration order are preserved. Repeated
  calls with the same bounded JSON request are deterministic.

Cycles, `Date`, boxed primitives, `BigInt`, `Symbol`, `undefined`, functions,
class instances, custom prototypes, `toJSON`, `toJSON5`, and callback behavior
cannot be represented faithfully by this JSON protocol and are out of scope.
The upstream tests for those values are source evidence only. A fresh child
per request also avoids relying on the parser's module-level lexer/parser
state across calls.

## Upstream TAP test evidence

The tracked suite consists of five CommonJS files using `tap` `12.6.0`:

```text
test/cli.js
test/errors.js
test/parse.js
test/require.js
test/stringify.js
```

A static scan found 55 `t.test(...)` declarations and 141 direct Tap assertion
calls. One loop expands a single source `t.throws(...)` call into nine runtime
assertions. Directly executing the five files with Node `22.23.1` emitted 204
`ok` TAP points and zero `not ok` points. Each process exited zero. This is a
source-behavior probe, not a frozen leaf count.

The declared test toolchain is not compatible with the locked Node v2 runtime.
After a disposable `npm ci --ignore-scripts`, the exact `npm run tap` command
failed before executing assertions:

```text
0 passing, 5 failing
TypeError: Function.prototype.apply was called on undefined
... node-spawn-wrap ... node-22 ...
```

The failure comes from the old Tap/coverage spawn wrapper under Node
`22.23.1`, not from a demonstrated parse/stringify regression. It means the
upstream command cannot be reused as the Node v2 verifier command or as a
frozen denominator.

The upstream suite is broader than the proposed task. It covers CLI file I/O
and subprocesses, global `require.extensions` mutation, callback revivers and
replacers, non-finite numbers, functions, boxed primitives, dates, custom
`toJSON`/`toJSON5`, cycles, and temporary output files. The future verifier
must author a separate private `node:test` adaptation over only the JSON
boundary, assign stable leaf IDs, collect the actual denominator in the final
runtime, and map every assertion to the public instruction. No upstream test
file or fixture is copied here.

## Committed npm lock and offline closure

The exact tree does contain `package-lock.json`, but it is npm lockfile version
1, not the required version 3. Its nested development graph has:

- 627 package-entry occurrences and 448 unique package names;
- 298 SHA-512 integrity values, 192 legacy SHA-1 values, and 137 bundled
  entries without their own integrity field;
- 490 HTTPS `resolved` values;
- seven optional entries; and
- all observed package entries marked development-only.

The root manifest declares 17 development dependencies and no
`dependencies`, `optionalDependencies`, or `peerDependencies`. The repository
Node bundle validator rejected the committed lock exactly as expected:

```text
npm dependency lockfile must use lockfileVersion 3
```

`npm ci --ignore-scripts` with npm `10.9.8` also warned that supplemental
metadata for the old lock had to be fetched from the registry and installed
490 packages. That network-resolved development tree is not an offline,
content-addressed verifier closure and cannot be promoted by this audit.

The zero-runtime-dependency package is nevertheless feasible for the narrow
runtime task. A disposable metadata-only probe removed scripts and development
metadata, generated an npm `10.9.8` v3 lock with one root `packages` entry and
zero dependencies, and then completed:

```text
npm ci --offline --ignore-scripts --no-audit --no-fund
```

against an empty cache. The temporary lock SHA-256 was
`5e3cfa1f431589311662cf1f45f6ff086a87716d7e681fd44cc0738a3f6a76f1`,
and a temporary empty-cache bundle using it was accepted by
`validate_npm_dependency_bundle`. This proves root-only runtime closure
feasibility; the hash is diagnostic evidence, not an approved artifact. No
generated lock, cache, bundle manifest, or installed dependency is stored in
this task directory.

## Lifecycle and build-script policy

The upstream manifest contains 12 scripts. Relevant commands include:

```text
build:          rollup -c
build-package:  node build/package.js
build-unicode:  node build/unicode.js
production:     run-s test build
prepublishOnly: npm run production
preversion:     npm run production
version:        npm run build-package && git add package.json5
```

There is no root `preinstall`, `install`, `postinstall`, `prepare`, `prepack`,
or `postpack` hook. Even so, the package is not acceptable unchanged:

- `build` creates the untracked `dist` browser/ESM artifacts;
- `build-unicode` rewrites tracked `lib/unicode.js` from development packages;
- `build-package` rewrites `package.json5`;
- `version` stages a file in Git;
- `prepublishOnly` and `preversion` chain tests and the Rollup build; and
- the current candidate tar validator rejects any `scripts` key, not only
  install hooks.

A source-only `npm pack --ignore-scripts` tarball was rejected with
`candidate lifecycle scripts are forbidden`. Therefore the later task must
require a script-free package manifest and must never run arbitrary candidate
scripts. The recommended CommonJS-only surface needs no build step. If a later
revision requires generated ESM/browser output, its exact toolchain and output
must be reviewed as a separate allowlisted build stage rather than being
silently executed through npm lifecycle behavior.

## Decision and later gates

Retain `json5` as a **CommonJS, JSON-only, development Node v2 candidate**. The
source-locked root implementation, MIT license, zero runtime dependencies, and
direct `parse`/`stringify` callability make the narrow task feasible. Do not
create a canonical manifest, Harbor bundle, dataset entry, or publication
claim from this record.

Before advancing beyond static authoring, a later approved lane must:

1. Write a public instruction that fixes the CommonJS root object and the
   finite JSON parse/stringify boundary, including error, quote, spacing,
   ordering, Unicode-warning, and output-size behavior.
2. Produce a reviewed, content-addressed npm `10.9.8` v3 root-only runtime
   lock/cache artifact. Do not reuse the upstream v1 development lock or the
   temporary hash above as a production artifact.
3. Require candidate packages to omit scripts, registry configuration,
   workspaces, loaders, native addons, browser/deep entry points, and generated
   ESM output.
4. Add a private verifier-owned `node:test` adapter, command artifact,
   structured report, traceability table, and automatically frozen leaf
   denominator. Do not reuse the failing Tap 12 command.
5. Run the Node Oracle and empty/stub/forgery/install-script/loader/hang/offline
   controls only in that later lane and separately from the Python dataset.
