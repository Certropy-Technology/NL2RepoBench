## Public behavior and JSON subprocess boundary

The public function has this source-level signature:

```text
parseNpmTarballUrl(url: string)
  -> { host: string, name: string, version: string } | null
```

The value surface fits the bounded JSON request/response protocol: the input is
one string, successful results contain only strings, and an unrecognized
registry-tarball path returns `null`. The function is stateless and has no
callback, filesystem, network, loader, or mutable-object protocol. Constructing
a WHATWG `URL` parses a string locally; it does not fetch the URL.

A future public contract still has to state the observable edge behavior
rather than merely say "parse an npm URL":

- an empty value fails the initial assertion with `url is required`;
- a truthy non-string fails with `url should be a string`;
- malformed or relative URL text can throw the platform `URL` error;
- malformed percent encoding can throw during package-name decoding;
- only paths with one `/-/` separator and a nonempty decoded package name are
  candidates for a result;
- scoped and percent-encoded scoped names are supported;
- version acceptance follows the dependency's loose SemVer validation, and
  the returned version is the filename slice rather than the normalized value
  returned by `semver.valid`;
- `host` follows WHATWG URL host semantics, including an explicit non-default
  port when present; no HTTP/HTTPS-only check exists in the source.

The checked Node runner can address the literal named export directly. In a
temporary built/install probe under Node `22.23.1`, both ESM `import()` and
Node's `createRequire()` exposed exactly one key:

```text
parseNpmTarballUrl: function
```

The repository's JSON subprocess client returned the expected object for a
simple tarball URL, returned JSON `null` for an ordinary non-tarball path, and
reported `AssertionError: url is required` as a bounded failed response for an
empty string. Selecting `default` failed with `export-is-not-callable`, as
expected. Therefore **direct callability is not the blocker** once a
policy-compliant built package exists; the lock, build, packaging, and private
verifier gates below remain unresolved.

## npm lock and offline cache closure

The exact source contains no `package-lock.json`, `npm-shrinkwrap.json`,
`npm-cache/`, or `bundle.manifest.json`. It is managed by pnpm instead:

- `devEngines.packageManager` requires pnpm `11` with `onFail: download`;
- the committed `pnpm-lock.yaml` uses lockfile version `9.0` and contains two
  YAML documents;
- the first document locks pnpm and `@pnpm/exe` to `11.0.8` and contains 19
  package entries, including 15 platform-constrained entries;
- the second document locks the application/development tree with 45 package
  entries; its root resolves runtime `semver ^7.6.3` to `7.7.4` and locks five
  development tools;
- the second document has 27 platform-constrained entries, primarily the
  optional esbuild packages used by `tsx`;
- `pnpm-workspace.yaml` explicitly permits the `esbuild` dependency build.

Neither pnpm lock document is an npm v3 lock or a verifier-owned offline npm
cache closure. The current Node v2 compiler requires `package-lock.json`,
`npm-cache/`, and `bundle.manifest.json`, tied to npm `10.9.8`, with all cache
entries present and installation forced to `--offline --ignore-scripts`.
Implicit Corepack/pnpm download is not permitted.

For diagnostic evidence only, forcing npm `10.9.8` past the package-manager
mismatch generated a temporary v3 lock with 43 non-root package entries,

`93ba445fa68650d0d3239b1457e856a15aab9d4f70781f91782e77d01a68c4f2`.
All 43 entries had SHA-512 integrity and HTTP(S) resolution, but the resolution
was based on current semver ranges rather than the committed pnpm versions. It
also contained 27 platform entries and two `hasInstallScript` entries. A

The temporary npm cache used for this diagnostic was not treated as an

## Lifecycle and candidate-package policy

The root scripts are:

```text
build:          rimraf lib && tsc
test:           tsx --test test/*.test.ts
prepublishOnly: pnpm run build
```

There is no root `preinstall`, `install`, `postinstall`, `prepare`, `prepack`,
or `postpack` script. That is not enough for this pilot:

- the checked-in package has no built public entry point, so publishing the
  exact package requires an explicit TypeScript build;
- `prepublishOnly` delegates that build to pnpm, while the verifier is locked
  to npm and no-network operation;
- the development tree includes esbuild and explicitly allows its dependency
  build;
- the current candidate tar validator rejects **any** `scripts` key, not only
  install hooks.

A temporary post-build tarball was passed to the repository package validator
and was rejected exactly as designed:

```text
NodeDependencyError: candidate lifecycle scripts are forbidden
```

A future task could explicitly require a prebuilt JavaScript ESM entry point,
a script-free manifest, and a committed npm v3 lock. That would be an authored
packaging adaptation, not the unchanged upstream package metadata, and it
needs review together with the private verifier. This static lane does not
silently make that product/protocol decision.

## Decision and reopen conditions

Do not create `task.toml`, `instruction.md`, a canonical manifest, or a Harbor
bundle for this candidate yet. Keep the lane **blocked** for these primary
reasons:

1. No accepted npm v3 lock/cache closure exists for the runtime dependency or
   the private verifier environment.
2. The frozen tree lacks its published `lib` entry point and depends on an
   unapproved TypeScript/pnpm build path.
3. npm `10.9.8` rejects the declared pnpm `devEngines` policy, and the current
   candidate package validator rejects the manifest's scripts.
4. The six TypeScript source tests are not a private boundary-driven
   `node:test` bundle with stable IDs, structured report, traceability, and a
   frozen leaf denominator.
5. No separate verifier, Oracle attempts, or empty/stub/forgery/lifecycle/
   loader/hang/offline controls were authorized or run.

The source lock, MIT license, narrow JSON value shape, and literal named
function export are suitable for a later authoring attempt. Reopen only after
approving the script-free built-package contract, reviewing an npm v3 offline
bundle, authoring private boundary tests and commands, and freezing collection
in the exact digest-pinned Node environment. Run Node Oracle and controls only
in that later lane and separately from the Python dataset.
