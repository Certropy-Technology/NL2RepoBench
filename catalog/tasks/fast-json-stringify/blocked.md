## JSON Schema Compiler Scope

The public API is a CommonJS callable factory:

```text
build(schema, options?) -> stringify(value) -> JSON text
```

The implementation validates and compiles JSON Schema-like input, then emits
specialized serializers for strings, integers, numbers, arrays, objects,
booleans, and nulls. The implementation also covers nested schemas and
features including `required`, `properties`, `additionalProperties`,
`patternProperties`, `items`, `$ref`, `allOf`, `anyOf`, `oneOf`, `if`/`then`/
`else`, `const`, `enum`, defaults, date/time formats, and large-array modes.
The README and type declarations additionally expose external schemas through
`options.schema`, Ajv settings through `options.ajv`, integer `rounding`,
`largeArraySize`, `largeArrayMechanism`, `mode: debug`, and
`mode: standalone`.

That is too broad to use as an implicit JSON-only task contract. Before
authoring, the public instruction must enumerate a smaller, traceable scope:

- Requests, schemas, options, and values are JSON values only: null,
  booleans, finite numbers, strings, arrays, and string-keyed objects.
- The adapter may allow a fixed subset of JSON Schema keywords and in-memory
  local `$ref` definitions. Remote or filesystem-backed references must not be
  reachable from the candidate.
- `Date`, `RegExp`, `BigInt`, `Symbol`, `undefined`, functions, class
  instances, custom prototypes, custom `toJSON`, callback options, and
  arbitrary Ajv callbacks/settings are outside the contract.
- `mode: debug`, `mode: standalone`, `restore`, and generated source text are
  outside the JSON response contract. The same applies to the
  `format: unsafe` path unless a separate contract explicitly permits output
  that is not valid JSON.
- The task must not claim that arbitrary user-provided schemas are safe. The
  upstream README explicitly treats schemas as application code because the
  compiler constructs executable code from them.

The module-level `largeArraySize` and `largeArrayMechanism` variables in
`index.js` are mutable across calls. A task adapter must use a fresh child for
each build-and-serialize request, or explicitly reset all compiler state; a
long-lived child cannot silently inherit one request's options into another.

## Dynamic Code Generation and Build Files

The locked source has multiple code-generation surfaces:

- `index.js:172-240` assembles JavaScript source from schema-derived strings,
  constructs a function with `new Function` at `index.js:233`, and returns the
  generated serializer.
- `index.js:223-229` exposes debug mode with generated source plus live
  `validator` and `serializer` instances. `index.js:1301-1304` restores that
  state with `Function.apply`.
- `lib/standalone.js:3-34` emits a CommonJS module containing
  `contextFunc.toString()`, serialized validator/serializer state, and deep
  imports such as `fast-json-stringify/lib/validator` and
  `fast-json-stringify/lib/serializer`.
- `build/build-schema-validator.js:1-26` invokes Ajv standalone generation and
  writes `lib/schema-validator.js`. The checked-in output is marked
  `CODE GENERATED BY 'build-schema-validator.js' DO NOT EDIT!`.

The root `package.json` has no `build` script, so the generator is not part of
the declared npm command path. Rebuilding it would require a separately
allowlisted, trusted build step and the exact Ajv toolchain. The candidate
verifier must not execute arbitrary package scripts or let the candidate select
the generator, loader, output path, or reporter. The seven tracked
`test/sanitize*.test.js` files are useful regression evidence for schema-string
escaping, but they do not replace a separate process boundary.

## Exports and Tests

The package metadata declares:

```text

```

There is no `exports` map. The root module assigns `module.exports`,
`.default`, `.build`, `.restore`, and `.validLargeArrayMechanisms` in
`index.js:1295-1304`. The absence of an `exports` map leaves internal paths
such as `lib/serializer`, `lib/validator`, and `lib/standalone` addressable;
standalone output relies on those deep paths. A task must specify which root
entry and callable operation are scored rather than inheriting every deep
import.

The upstream test tree is not a frozen Node v2 denominator:

- There are 55 `.test.js` files. A source scan found 368 direct `test(...)`
  call sites and 26 nested `t.test(...)` call sites. Several direct calls are

  dates, regular expressions, BigInts, symbols, `undefined`, custom

## JSON Subprocess Boundary

The repository's development Node helper uses an allowlisted runner with a
bounded JSON request/response, `--no-addons`, a sanitized environment, and
fixed package/export names. The current limits are 64 KiB per request, 256 KiB
per response, and at most 32 arguments; the test-side client additionally
runs the child as the unprivileged candidate user with CPU/process/file limits.
These helpers are shared development infrastructure, not a
`fast-json-stringify` task artifact.

The generic one-call protocol is not sufficient for this package. The root
export is a factory: calling `default` or `build` with a schema returns a
JavaScript function. That function cannot cross a JSON response boundary, and
`restore` requires live Ajv/Serializer instances. A task-specific private
client is required to perform a fixed operation inside the child, for example:

```text
{ "op": "stringify", "schema": <JSON>, "options": <JSON>, "value": <JSON> }
  -> { "ok": true, "value": <JSON string> }
```

The client must call the package factory and returned serializer in the same
child, return only JSON data, reserve stdout for the protocol, and report
exceptions through a bounded structured response. It must not accept arbitrary
filesystem paths, package names, exports, loaders, generated source, Ajv
instances, callbacks, or network-backed references. A fresh child per request
also isolates the compiler's mutable module-level options.

No `fast-json-stringify`-specific client, private test bundle, command plan,
frozen collection, or separate verifier exists in this task directory.
